## 1. 验收项 1：一条真实存量表 → 另一张表的全量搬运跑通，行数对账一致

**用例**：`com.zifang.z.etl.core.FullLoadReconciliationTest#fullLoadMovesAllRowsAndReconciles`

| 环节 | 事实 |
|---|---|
| 源表 | `z_trade_order` —— **表结构照生产真实表形状**（字段集与类型对齐 `z-opc/_doc/004_sql/z-trade.sql` 里那张表），数据**本地生成 1000 行** |
| 目标表 | `etl_trade_order_snapshot`（幂等键 `order_id` 上有主键约束） |
| 数据源 | 两个**独立**的 H2 内存库 ⇒ 真的跨数据源搬运 |
| 结果 | 读 1000 行 / 写 1000 行；源 1000 行 = 目标 1000 行；**校验和一致**（双口径） |
| 抽查 | `id → order_id` 改名映射正确；`amount` 保持 `BigDecimal` 精度（`101.00`）；`status` 归一成 `INT` |

> 生产库里那张 `z_trade_order` **一个字节都没碰**：本轮不连生产、不建生产表（卡面硬边界）。

## 2. 验收项 2：job 描述 JSON/yml 可落库、可重跑；重跑幂等（不重不漏）

**用例**：`com.zifang.z.etl.core.IdempotentRerunTest`（3 个用例）

| 子项 | 事实 |
|---|---|
| 可落库 | 描述写进 `etl_job_def`（JSON + yml 两份文本），取回后字段一致；`listNames()` 可见 |
| 可重跑 | 落库后**按作业名**跑（不依赖原始描述文件），写 1000 行，履历 `etl_job_run` 有记录 |
| 幂等（增量重跑） | 首跑落水位后，第二次 `auto` 跑自动切增量，源表无新数据 ⇒ **读 0 行**，目标行数仍 1000 |
| 幂等（强制全量重跑） | `mode=init` 重读全表 1000 行并按幂等键 upsert ⇒ 目标仍 **1000 行**，且 `COUNT(DISTINCT order_id) = 1000`（**不重不漏**），对账仍一致 |

## 3. 验收项 3：首跑后自动切增量模式（水位记录可见）

**用例**：`com.zifang.z.etl.core.IncrementalSwitchTest`（2 个用例）

| 子项 | 事实 |
|---|---|
| 首跑 | `mode=init`（全量 1000 行），对账一致 |
| 水位可见 | `etl_job_checkpoint` 落一行：`watermark_column=updated_at`、`watermark_type=TIMESTAMP`、`watermark_value=<首跑末位时间戳>`、`last_mode=init` |
| 自动切增量 | 源表新增 5 行后，第二次跑 `mode=incremental`，**只读 5 行 / 写 5 行**，目标 1005 行，对账一致 |
| 水位推进 | 跑完水位值向前推进，且与运行结果里的 `watermarkAfter` 一致 |
| 反向闸门 | 声明 `mode=incremental` 但**无水位** ⇒ 直接失败（不静默退化成全量） |
