# 验收复跑 · 水位轮询 + 持久化断点续传（TASK-20261012-014 / D3）

> 卡面纪律：**binlog CDC 一行代码都不写**（M3 另拆卡）。本仓只做「水位轮询 + 断点续传」。
> 全部验收在**本地 H2** 上跑（内存库跑增量语义，文件库跑跨进程 kill/resume），
> **不连任何真实库 / 生产库**。

---

## 1. 水位模型

| 部件 | 落点 | 说明 |
|---|---|---|
| 游标键（job 级配置） | `WatermarkSpec`（`column` / `type` / `tiebreakColumn`） | `update_time`（TIMESTAMP）或自增 id（LONG）二选一；**平局列**是复合游标的第二键 |
| 游标值持久化 | `etl_job_checkpoint` 表（`JdbcCheckpointStore`） | `watermark_value` + `tiebreak_value` + `last_mode` + `last_run_at`（上次推进时间） |
| 复合游标 | `checkpoint/WatermarkCursor` | 「水位值 + 平局列值」字典序比较；归一（LONG→Long，TIMESTAMP→Timestamp） |
| 读面过滤 | `reader/JdbcRowReader` | 精确口径 `(w > ?) OR (w = ? AND tb > ?)`；回溯口径 `w >= 水位 − overlap` |
| 排序 | `JdbcRowReader#effectiveOrderBy` | 复合游标时 `ORDER BY 水位列, 平局列` ⇒ 排序键唯一 ⇒ 翻页不漏行 |

**为什么必须带平局列**：单键时间游标的过滤条件是 `w > 已存水位`，
同一秒写进源表的多行里，**时间戳等于水位的那批会被永久漏掉**（它们既不 `>` 水位，也没有更晚的时间戳）。
配了平局列（自增 id）后，同秒的行按 id 依次接力，不漏行 —— 实测见 §3.1。

## 2. 轮询执行（失败不推进 = 断点续传语义）

```
读一页 → transform → 写目标 → flush（提交）→ **推进水位（落 etl_job_checkpoint）**
```

- **成功才推进**：水位在**本页写入并提交成功之后**才落库（`EtlEngine` 的页级回调里）。
  写失败 ⇒ 抛异常 ⇒ **本页的水位不推进**，水位停在上一个成功页。
- **重启从断点继续**：进程被 `kill -9`（没有 finally、没有优雅退出）后重启，
  水位已持久化 ⇒ 增量轮从断点之后接着搬，不从头再来。
- **可重不漏**：目标侧是 upsert（幂等键 `idempotencyKey`）⇒ 失败页重搬是幂等的。

## 3. 四类边界行为（实现落点 + 可判据）

| 边界 | 行为 | 实现落点 | 可判据？ |
|---|---|---|---|
| **同秒多条** | 复合游标（`tiebreakColumn`）按平局列接力，同秒的新行照搬不漏 | `WatermarkCursor` + `JdbcRowReader` 过滤/排序 + `watermark.tiebreakColumn` 配置 | ✅ 有实测（`WatermarkBoundaryTest#sameTimestampRowsNeedTiebreakColumn`，含「单键游标会漏」的对照组） |
| **时钟回拨 / 迟到数据** | ① 检测：源/目标行数有落差时报「未搬过去的行数」+「游标之前压着的行数」，并给出告警 note；② 兜底：配 `watermark.overlap`（秒）开**回溯窗口**，窗口内的迟到行会被重读并幂等 upsert；③ 窗口外的迟到行**搬不到**（纯时间游标的固有局限），口径：改用自增 id 游标或人工重置水位 | `EtlEngine#countRowsBehindCursor` + `JdbcRowReader` 回溯口径 + `WatermarkSpec#overlap` | ✅ 有实测（`WatermarkBoundaryTest#clockRollbackIsDetectedAndRecoverableWithOverlap`：默认口径报出 1 行滞留 + 告警；开 overlap 后补捞成功且对账一致） |
| **游标越界（源表被清）** | 默认 `onOutOfRange=FAIL`：**明确抛错**（错误信息带「游标越界」「不推进水位」）且**水位保持原值**；显式配 `RESET` 才清掉水位、本轮退回全量重跑 | `EtlEngine` 越界检测 + `SourceWatermarkStats` + `WatermarkSpec#onOutOfRange` | ✅ 有实测（`WatermarkBoundaryTest#outOfRangeFailsWithoutAdvancingWatermark`） |
| **失败不推进（断点续传）** | 写失败的那一页**不推进水位**；此前成功页的推进保留（这正是断点续传）；修好后重跑从断点继续 | `EtlEngine` 页级回调（先 flush 再落水位）+ `reader/PageHandler` | ✅ 有实测（`WatermarkBoundaryTest#failedPageDoesNotAdvanceWatermark`：坏行落在第 5 页 ⇒ 目标只提交前 4 页；修好后重跑对账一致）+ 跨进程 kill 实测（§4） |

## 4. 三项验收标准的实测

| 验收标准 | 测试类 | 实测结果 |
|---|---|---|
| 源表持续写入场景下，增量轮只搬新行（行数对账零差异） | `WatermarkIncrementalOnlyNewRowsTest` | 首跑全量 500 行；并发写入 300 行的同时跑增量轮 ⇒ 增量轮**读数 == 写数**（老行零重搬）；三轮搬运行数之和 == 源表总行数 800；最终源/目标行数相等、校验和相等（零差异） |
| 搬运中途 kill 进程，重启后从断点继续，最终对账一致 | `WatermarkResumeAfterKillTest`（子进程 `WatermarkKillResumeChild`） | 子进程跑增量搬运，父进程在它提交了若干页后 `kill -9`（SIGKILL）⇒ 水位已推进（页级提交落盘）、搬运未完成；**重启**（新进程）从断点继续 ⇒ 源/目标行数相等（40000 == 40000）、`reconciled=true` |
| 游标持久化可查（当前值 / 上次推进时间） | `WatermarkCheckpointVisibilityTest` | 两条路径都查得到：存储口 `JdbcCheckpointStore#load` 与直查 `etl_job_checkpoint` 表；水位当前值向前推进、`last_run_at` 刷新、`last_mode` 可查 |

**kill 实测的两个关键细节**（踩过的坑，写在这里免得后人再踩）：
1. H2 的 MVStore 默认 **1 秒才刷盘** ⇒ 被 SIGKILL 时最后一段提交会丢 ⇒ 文件库必须带
   `WRITE_DELAY=0`，并且每落一次水位就 `CHECKPOINT` 一次（见 `WatermarkKillResumeChild`）。
2. 跨进程接力只能靠 **H2 文件库**（内存库随进程一起没了 ⇒ 证明不了续传）；
   同时父进程不能持有该库的连接（H2 文件库同刻只允许一个进程打开）。

## 5. 与 z-schedule 的接法

- **调度交 z-schedule，本仓不自造调度器**：z-etl 只提供「跑一轮增量」的能力
  （`EtlEngine#run`），触发方式由 z-schedule 决定（HTTP 调 `POST /api/etl/jobs/{name}/run`
  或直接调引擎）。
- 本卡**未改动 z-schedule 仓任何文件**。
